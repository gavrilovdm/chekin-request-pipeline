What happens after a worker takes a request off the queue

A public API accepts requests from thousands of tenants. Postgres holds the truth, RabbitMQ only carries ids, and stateless asyncio workers claim, process and record each request exactly once in effect.

Components

Three services from one codebase plus two pieces of infrastructure. The sweeper is the safety net: any request that the queue lost, that is due for retry, or whose worker died is found in Postgres and re-enqueued.

Worker flow

The message is only a hint. The worker trusts Postgres: a conditional UPDATE … RETURNING claims the request with a lease, and the completion is accepted only if the worker still holds that lease (attempt works as a fencing token).

  participant DS as downstream
  Q->>W: deliver {request_id}
  W->>DB: claim: status→processing, attempt+1, locked_until=now+lease
WHERE claimable OR lease expired
  alt 0 rows: finished or held by another worker
    W->>Q: ack, skip
  else claimed, attempt > max (crash loop)
    W->>DB: complete → needs_human
    W->>Q: ack
  else claimed
    W->>DS: process(payload), timeout, Idempotency-Key = request_id
    DS-->>W: result / retryable error / permanent error
    Note over W: classify → done · retry_scheduled(next_attempt_at) · failed · needs_human
    W->>DB: complete WHERE status=processing AND attempt=n
    W->>Q: ack
  end

Request states

stateDiagram-v2
  direction LR
  [*] --> received: POST accepted
  received --> processing: claim
  retry_scheduled --> processing: claim when due
  processing --> processing: lease expired, re-claim
  processing --> done: success
  processing --> failed: permanent error
  processing --> retry_scheduled: retryable error, attempts left
  processing --> needs_human: attempts exhausted
  done --> [*]
  failed --> [*]
  needs_human --> retry_scheduled: operator replay
  needs_human --> [*]

There is no queued state: received means accepted and maybe published. Duplicate publishes are harmless because the claim lets only one through. That saves one write per request.

Scaling

Capacity math

  • 280 rps × 0.5 s downstream ≈ 140 requests in flight
  • Planned: 50 in flight per worker → 3 workers on average, ~15 at peak
  • Measured: a worker process is CPU-bound at ~120 req/s → 3 worker cores on average, ~12 at peak
  • ≈3 DB writes per request → ~1k writes/s, ~5k at peak

Why asyncio in one process

  • The work is I/O-bound: waiting on Postgres and the downstream
  • Threads add GIL contention and memory for no gain here
  • Processes are for CPU-bound work; we scale by containers instead

Limits of each unit

  • Coroutine: blocked by any sync call; capped by the semaphore
  • Process: one CPU core (GIL), its own memory and connection pool
  • Container: CPU and memory quota; DB connections are the shared ceiling
